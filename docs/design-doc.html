02

创意背景与痛点

起点：一个计算机大四学生的秋招日常

投了 30 多家，手机里躺着四个东西：一个记投递的 Excel、一个存 JD 截图的相册、一个名叫「八股」的备忘录、 以及一个每天刷三次却始终没有红点的邮箱。秋招进行到一半，真正折磨人的已经不是"没 offer"， 而是完全不知道自己卡在哪一环——是简历没被看见？是笔试差一点？还是面试表达不行？

这种状态有个准确的名字：无反馈的努力。学生做的最常见应对是"再海投 50 家"， 结果是把同一个错误重复 50 次。

三个被现有工具忽视的痛点

01

投递是黑盒：投了几十份零面试，归因全靠猜

市面上的求职 APP 都在做"岗位聚合"（把更多岗位推给你），但没人做"投递结果归因"。学生无法回答一个最基本的问题：我这一版简历，到底有没有在起作用？改简历全凭感觉，改完还是投同一个黑洞。

02

面试不复盘：同一个知识点能栽三次

面完一场，情绪耗尽，什么都不想记。两周后下一场面试，被问到同类问题依然卡壳。面试产生的信息是这个阶段最贵的资产，却在 24 小时内蒸发。没有结构化的复盘手段，也就没有"补强清单"，学生只能泛泛地"再刷点八股"，效率极低。

03

节奏靠记忆：秋招窗口在压缩，岗位"招满即下架"

2026 年秋招的一个显著变化是节奏前移与集中：头部企业正式批在 8 月底至 9 月初开启，部分核心岗位开启后一到两周即招满关闭。学生的笔试、面试、投递截止日期散落在十几个平台通知里，靠脑子记必然漏，而漏掉的每一个都可能是一个 offer。

04

核心功能设计

砍到 12 天能做完的范围
◈
范围纪律：本作品按 1 人 × 12 天 × 每天 6 小时 ≈ 70 工时设计。凡是需要后端服务、需要外部数据抓取、需要真机传感器的功能，一律不做——不是不想做，是做了就是半成品，而完备度占 20 分。

MVP 四件套（必须全部完成）

P0 · 数据入口

① 投递快记

从桌面卡片直达，3 秒完成一条投递记录：公司 / 岗位 / 渠道 / 简历版本 / 当前状态。提供快捷标签与键盘上推即存的交互。

为什么是 3 秒：记录类产品的死亡原因永远是"太麻烦，明天再记"。所有设计让位于缩短录入路径。
P0 · 可视化

② 作战地图

把全部投递渲染成漏斗 + 时间轴的复合视图：投递 → 已读 → 笔试 → 一面 → 二面 → Offer，每一层标注转化率，异常节点自动标红。

这是全片的视觉钩子：手机上是紧凑列表，平板上一展开就是一张完整的作战地图，两个形态差异极大——一多部署的价值一眼可见。
P0 · 产品灵魂

③ 面试复盘 → 能力雷达

面试后 90 秒勾选"被问到什么 + 我答得如何"，累积生成能力雷达图，自动排出最该补的 3 个短板并给出补强顺序。

这是本作品真正的创新点：把"我好像哪里都不行"的弥散焦虑，收敛成一张能照着执行的清单。市面上没有任何求职产品在做这件事。
P0 · 鸿蒙特色

④ 节奏哨兵

投递截止 / 笔试 / 面试三类节点统一进入提醒体系：桌面卡片常驻显示最近 3 个节点与实时倒计时，临近节点由本地通知推到锁屏与横幅。

对应"岗位招满即下架"的现实：错过的截止日期是真实的 offer 损失，这个功能的付费意愿最强。

加分项（做完 MVP 有余力才碰）

P1

⑤ 简历版本 A/B 对比

同一份简历的不同版本分别追踪回复率，并排对比"改了什么 → 结果有什么变化"。

这是"把海投变成小实验"最直接的落地形式，若时间允许优先做它。
P2

⑥ JD 匹配度速诊

粘贴 JD 文本，本地关键词提取后与能力雷达比对，输出"匹配度 + 该补什么"。

纯本地规则实现，不依赖大模型接口，可控性强。

明确不做（红线清单）

  • 不做账号体系与云同步 —— 纯本地存储。数据敏感（薪资、简历），本地化反而是卖点。
  • 不做岗位抓取 / 爬虫 —— 合规风险 + 时间不可控。
  • 不接大模型 API —— 网络依赖 + 成本 + 演示不可控，12 天内是负债。
  • 不碰 NFC / 扫码 / 相机 / 分布式协同 —— 模拟器不支持，演示不出来的能力等于不存在。

已核实并排除：实况窗（Live View Kit）

实况窗（状态栏胶囊 + 锁屏卡片）本来是"节奏哨兵"最理想的落地形态，但它不是技术问题，而是资质问题。 按 HarmonyOS 官方文档（Live View Kit 简介 / 开通实况窗服务权益，2026-08 更新）逐项核对后确认：

官方限制对本作品的影响
场景白名单 仅 16 类场景开放申请。面试倒计时唯一能挂靠的是「计时（TIMER）」，而该场景仅限工具类应用申请，官方明确列出不适用情形包含事项待办、会议日程提醒、课程提醒。
总时长 ≤ 8 小时 单实例生命周期最长 8 小时，且超过 2 小时未更新会隐藏胶囊、超过 4 小时未更新直接清除。无法实现"提前 24 小时进入倒计时"的设想。
需要资质审批 接入与调测前须在 AppGallery Connect 提交权益申请（含场景描述与设计规范归档），5 个工作日出结果；通过后还需重新生成 Profile 并重新打包。这在 12 天工期内不可控。
仅前台可创建 本地实况窗要求应用处于前台且已产生服务合约，无法由后台自行唤起。
◈
处置：砍掉，不做降级保留。把"节奏哨兵"的实现改为卡片常驻倒计时 + 本地通知——两者均无需任何资质审批，退回模拟器即可完整演示。 代价是失去状态栏胶囊的"长效常驻感"，但锁屏可见性仍然保住。省下的工时全部投入服务卡片与多端适配，因为砍掉实况窗之后，创新分的两根支柱就是它们。
若后续有余力，可在 D9 顺手提交一次权益申请当作加分项，但方案主体绝不依赖它。
◈
API 名称已核实。本节涉及的 FormKit、NotificationKit、@kit.LiveViewKit 均已对照华为官方文档确认存在与命名。 仍建议在动手前用官方文档复查各接口的版本起始号（部分卡片动效能力有版本门槛），不要在 PPT 里写未验证的 API 名——答辩时被技术专家追问会很难看。
06

交互创新点

创新性 50 分的主战场

创新点一：把系统桌面当成产品的首页

传统应用的信息架构是"打开 App → 找功能"。灯塔的第一个界面不是 App 首页，而是手机主屏上的那张卡片： 最上面是最近的三个节点倒计时，中间是本周投递数与回复率，右下角一个「＋」。

这个设计的价值不在于节省一次点击，而在于把"求职进度"从一个需要被想起的东西，变成每次解锁都会撞见的东西。 焦虑的反面不是放松，是确定性——用户每次看到卡片，都在确认"我掌握着局面"。

创新点二：让倒计时常驻在桌面，而不是关在应用里

求职者当天的状态是"不敢错过"，这个需求最合理的落点是把时间信息推到不需要主动打开任何应用的地方。 灯塔用两层承接：桌面服务卡片常驻显示最近三个节点与实时倒计时，节点临近时再由本地通知推到锁屏与横幅。

真正要下功夫的是卡片的刷新策略：倒计时靠定时轮询会耗电且不准，需要结合系统提供的卡片定时刷新能力做分钟级更新， 并在节点发生状态跃迁（例如"距截止不足 2 小时"）时主动触发刷新。 这类工程细节是评委区分"真做过"与"套了个壳"的地方。

◈
关于实况窗的取舍（答辩大概率被问）：实况窗本来是这件事最理想的形态，但官方场景白名单不接受"事项待办 / 会议日程提醒"类场景， 且需 5 个工作日资质审批，在 12 天工期内不可控。 用卡片 + 通知拿到 80% 的效果，同时主动放弃一个更强但不合规的能力——这个判断过程本身就是工程成熟度，答辩时讲出来远比藏着有说服力。

创新点三：折叠屏悬停 = 面试作战台

线上面试时，手机通常是立在桌上的。折叠屏半折悬停恰好是这个物理姿态：

  • 上半屏：这家公司的 JD 关键词高亮 + 上次面试暴露的短板提醒（看着它回答问题）
  • 下半屏：剩余时间倒计时 + 结束后立刻可用的速记区

面试结束不需要换设备、不需要切换状态，倒计时停下的那一刻，复盘入口就在手指下面。这把"面试"和"复盘"两个动作缝在了一起，也是雷达图能持续更新的原因。

创新点四：一张会自己长大的雷达图

雷达图的六个维度不是预设的教科书目录，而是从用户自己的面试记录里长出来的——数据库设计、Java 并发、项目表达、 算法、计算机基础、沟通。哪一维被问得多、答得差，它就会自动收缩，并置顶到"该补清单"的第一位。

这让产品的输出从"你要努力"变成"你下周先补 MySQL 的锁"——可执行，是这一代求职工具最缺的东西。

两个需要提前想清楚的技术点

① 卡片与 App 的数据一致性

卡片是独立进程运行的，和 App 不是同一份内存。写入流程必须约定清楚：App 写库 → 主动通知卡片刷新 → 卡片重新读库。 如果只在 App 侧更新而不推卡片，桌面会显示过期数据——这是同类作品最常见的翻车点，也是答辩时展示"技术深度"的好素材。

② 雷达图的归一化

"被问次数"和"自评分数"是两个量纲，直接相乘会失真。方案：短板指数 = 提问频次归一值 × (1 − 自评归一值)， 取指数最高的前三项作为"该补清单"。这个公式写在文档里，答辩时可以直接讲。

答辩预演

复赛形式：线下路演 + 答辩
Q1市面上已经有牛客、BOSS、应届生求职网，你凭什么做这个？
那些产品做的是"把岗位推给用户"，解决的是信息获取；灯塔做的是"把投递结果还给用户"，解决的是反馈缺失。 这是两个完全不同的环节——你可以在所有平台上投递，但没有任何一个平台会告诉你：你这一版简历的回复率是多少、你最该补的能力是哪一项。 灯塔不抢流量入口，它是求职过程的数据层。
Q2为什么非要用鸿蒙？做成小程序不是一样？
不一样，而且差别正好在产品最核心的地方。求职是一场"不敢错过"的等待，它的信息必须出现在用户不需要主动想到的地方。 小程序做不到两件事：一是把进度和倒计时钉在手机桌面（服务卡片作为主入口，而不是应用图标）， 二是让同一份数据在手机、平板、折叠屏上呈现三种不同的工作姿态（一次开发多端部署）。 这两个能力决定了产品的根本形态——是"一个需要被打开的工具"，还是"一个一直在你身边的助手"。灯塔必须是后者。

另外坦白一句：我们原本还想用实况窗把倒计时放进状态栏，但它的场景白名单不接受"事项待办 / 会议日程提醒"， 且需 5 个工作日资质审批，所以主动砍掉了。我们不是"没想到更好的方案"，而是核实过、判断过之后选择了合规的那条路。
Q3雷达图的算法依据是什么？会不会很主观？
它由两部分构成：客观部分是提问频次（一场面试里这个知识点被问了几次），这是事实数据； 主观部分是自评掌握度，这是用户对自己的判断。短板指数 = 频次归一值 ×（1 − 自评归一值）。 产品的目的不是给出一个"客观的能力评分"，而是把用户的注意力排序——先补被问最多、又答得最差的那些。这个排序比绝对分数更有用，也更诚实。
Q4你一个人 12 天，凭什么能做完？
因为我把范围砍得很狠。整个作品没有后端、没有账号、没有网络请求、不接大模型，是一个纯本地应用—— 数据存在设备里既是隐私设计，也是工期设计。四个核心功能全部围绕一条主数据流展开，共用同一套数据层。 另外我有 HarmonyOS 应用开发者基础与高级认证的技术储备，ArkTS 和 ArkUI 不是从零开始。
Q5这个项目接下来准备怎么做下去？
三条线。第一，真机 + 上架：补齐服务卡片动效与倒计时刷新策略的真机验证，冲击应用市场，先在自己的学校跑起来。 实况窗在取得服务权益资质后作为下一版能力接入（它是这件产品最理想的形态，只是当下批不下来）。 第二，数据积累：真实投递数据积累一季后，可以做"什么样的简历版本回复率更高"的群体洞察，这是这个产品真正的护城河。 第三，转向高校就业中心：把个人工具升级为学院级的求职态势看板，直接服务"高质量充分就业"的考核需求。
